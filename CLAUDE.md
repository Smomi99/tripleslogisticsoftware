## 4. GLOBAL DATABASE CONVENTIONS

1. **Keep the client's field meaning; normalize the naming.** The client spec writes
   `Port_ID_no`, `Customer_PIC_Name`. Store as `snake_case` columns (`port_id`, `pic_name`) but
   **never drop, rename, or merge a field the client listed**. Keep a mapping comment in
   `schema.prisma` above each model: `// client: Table_Port_List`.
2. **Every table gets:** `tenant_id` (BIGINT FK → `tenant`, **first column, indexed, NOT NULL** —
   see §7A), `id` (BIGSERIAL PK), `code` (human-readable business ID, e.g. `PL-001`, generated by
   sequence **per tenant per table**), `is_active BOOLEAN DEFAULT true`, `created_at`, `updated_at`,
   `created_by`, `updated_by`, `deleted_at` (nullable — soft delete only).
   Exceptions (platform-level, no `tenant_id`): `tenant`, `plan`, `plan_feature`, `subscription`,
   `subscription_invoice`, `payment`, `permission`, `platform_user`.
3. **Never hard-delete.** The spec's `Action` column is `Edit` + `Active/Inactive` only.
   Deactivation must never break historical FKs.
4. **Every dropdown value listed in §5–§6 becomes a Postgres enum or a lookup table.** Use a lookup
   table when the client may add values later (carrier type, cost unit, network member); use an
   enum only for closed sets (port type).
5. **Foreign keys are mandatory and `ON DELETE RESTRICT`.** No orphan rows, ever.
6. **Money & rates:** `NUMERIC(18,4)`. Never `float`. Store the currency id alongside every amount.
7. **Audit trail:** one `audit_log` table (`table_name`, `record_id`, `action`, `changed_by`,
   `old_values JSONB`, `new_values JSONB`, `created_at`), written by a Prisma middleware for every
   create/update/deactivate.
8. **Indexes:** on every FK, on every column exposed by the screen's Search box, and a
   `GIN (to_tsvector(...))` index where the search is free-text over names.
9. **Every unique constraint is composite with `tenant_id`.** `UNIQUE(tenant_id, code)`,
   `UNIQUE(tenant_id, port_code)`, `UNIQUE(tenant_id, username)`. A bare `UNIQUE(email)` on a
   tenant table is a bug — two different companies may employ the same person.
10. **Every FK must point within the same tenant.** Enforce with composite FKs
    (`FOREIGN KEY (tenant_id, carrier_id) REFERENCES carrier(tenant_id, id)`) or a checked
    constraint. Cross-tenant leakage through a join is the single worst failure mode here.

## 7. RBAC — GRANULAR, SUPERADMIN-CONTROLLED (critical requirement)

The superadmin must be able to pick, **per user and per individual feature**, exactly what that
user can reach. Role templates exist for speed, but per-user overrides always win.

### Permission model

```
module        e.g. SETTING, CRM, PURCHASE
feature       e.g. CRM.CUSTOMER, SETTING.CARRIER, PURCHASE.PRICE_LIST_FCL   (one per screen)
action        VIEW | CREATE | EDIT | TOGGLE_STATUS | DELETE | EXPORT | APPROVE
permission    "<FEATURE>.<ACTION>"   e.g. "CRM.CUSTOMER.EDIT"
```

Tables:

```
role                    id, name, description, is_system
permission              id, module, feature, action, key(unique)   ← seeded from a code constant
role_permission         role_id, permission_id
user                    id, employee_id FK, username, email, password_hash, role_id,
                        is_superadmin, is_active, last_login_at
user_permission         user_id, permission_id, effect ENUM('ALLOW','DENY')   ← per-user override
```

### Resolution order (implement exactly)

1. `is_superadmin = true` → **all permissions, always**. Never check further.
2. Start with the union of the user's role permissions.
3. Apply `user_permission` rows: `ALLOW` adds, `DENY` removes.
4. `DENY` beats everything except superadmin.
5. Inactive user or inactive role → no access.

### Enforcement — all four layers, no exceptions

- **API middleware:** `requirePermission('CRM.CUSTOMER.EDIT')` on every route. A route with no
  permission guard is a bug.
- **Server components / server actions:** re-check before returning data. Never trust the client.
- **Navigation:** the sidebar renders only modules/features where the user holds `.VIEW`. A module
  with zero visible features is hidden entirely.
- **UI controls:** hide (not just disable) Add / Edit / Activate buttons the user lacks.

### Superadmin screens to build

1. **Roles** — list, create, and a permission matrix (rows = features grouped by module,
   columns = actions, checkboxes, select-all per row and per column).
2. **Users** — list, create (link to an employee record), assign role, activate/deactivate,
   reset password.
3. **User Permissions** — the same matrix for one user, showing three states per cell:
   *inherited from role* (grey check), *explicitly allowed* (green), *explicitly denied* (red).
   Include a "reset to role default" action.
4. Cache the resolved permission set in the JWT/session, and **bust the cache immediately** when a
   role or user permission changes.

## 7A. MULTI-TENANCY (build this first — it is not a later feature)

**Model: single database, shared schema, `tenant_id` on every business table, enforced by Postgres
Row-Level Security.** Chosen over schema-per-tenant (migration pain across hundreds of schemas) and
DB-per-tenant (cost, ops burden for a 2-person team). Revisit only if a client demands physical
isolation — then move that one tenant to its own DB, same code.

```
tenant        id, name, slug (subdomain), country, timezone, currency_id,
              status ENUM('TRIAL','ACTIVE','PAST_DUE','SUSPENDED','CANCELLED'),
              trial_ends_at, logo_file, created_at
platform_user id, email, password_hash, name, is_active   ← YOUR staff, not a customer's
```

Rules:

1. **`tenant_id` is resolved server-side from the session, never from a request body or query
   param.** A client that can send `tenant_id` can read another company's shipments.
2. **Postgres RLS is the safety net, not the primary control.** Enable RLS on every tenant table
   with `USING (tenant_id = current_setting('app.tenant_id')::bigint)`, and have the API set
   `app.tenant_id` at the start of every transaction. Application-level scoping is layer one; RLS
   catches the query where a developer forgot the `where`.
3. **Prisma:** wrap every client in a tenant-scoped extension that injects `tenant_id` into every
   `where`, `create`, and `update`. Never expose the raw client to feature code.
4. **Write an isolation test per module** — seed two tenants, authenticate as tenant A, assert every
   list endpoint returns zero rows of tenant B. This test suite is mandatory before any module ships.
5. **Routing:** subdomain per tenant (`acme.yourapp.com`), custom domain support later. Resolve the
   tenant in Next.js middleware and pass it through the session.
6. **Seeding a new tenant** is one transactional function: create tenant → seed default roles +
   permissions → seed lookup values (cost units, carrier types, currencies, port list if shared) →
   create the first admin user → send invite email. Onboarding must be zero-touch by launch.
7. **Global vs tenant-owned master data:** ports, currencies, and carriers are the same worldwide.
   Give these tables a nullable `tenant_id` — `NULL` means a system row visible to all tenants,
   non-null means the tenant's own addition. Tenants may deactivate a system row for themselves
   (via a `tenant_master_override` table) but never edit or delete it.

## 7B. SUBSCRIPTION, PLANS & FEATURE GATING

```
plan                  id, name (Starter/Professional/Enterprise), price_monthly, price_yearly,
                      currency, max_users, max_shipments_per_month, max_storage_mb, is_active
plan_feature          plan_id, feature_key   ← which §7 features the plan unlocks
subscription          id, tenant_id, plan_id, billing_cycle ENUM('MONTHLY','YEARLY'),
                      status ENUM('TRIALING','ACTIVE','PAST_DUE','CANCELLED'),
                      current_period_start, current_period_end, cancel_at_period_end
subscription_invoice  id, subscription_id, amount, currency, status, due_date, paid_at, pdf_file
payment               id, invoice_id, gateway, gateway_ref, amount, status, paid_at
tenant_usage          tenant_id, period, users_count, shipments_count, storage_mb  ← rolled up nightly
```

**Access = plan entitlement ∩ user permission.** Both must pass:

1. Is the feature in the tenant's `plan_feature` list? If not → upgrade prompt, not a 403 page.
2. Does the user hold the §7 permission? If not → hidden / 403.

Superadmin (tenant-level) bypasses **permissions**, never **plan limits**. Only `platform_user`
bypasses plan limits.

Other rules:

- **Enforce seat and volume limits at creation time**, with a clear message: "Your Starter plan
  allows 5 users. Upgrade to add more." Never fail silently.
- **Lifecycle:** `TRIAL` (14 days, full features) → `ACTIVE` → `PAST_DUE` (grace period, banner,
  still writable) → `SUSPENDED` (**read-only + export only, never delete data**) → `CANCELLED`
  (data retained 90 days, then purge job).
- **Payments:** abstract behind a `PaymentGateway` interface from day one. Bangladesh market needs
  bKash / Nagad / SSLCommerz; international needs Stripe. Never hardcode one gateway's fields.
- **Every tenant can export all its own data** (CSV/Excel per module). Legally and commercially
  non-negotiable for SaaS.
- **Platform admin console** (separate app or `/platform` route, `platform_user` only): tenant list,
  create/suspend tenant, change plan, view invoices, impersonate a tenant user for support —
  **impersonation must be logged to `audit_log` every single time**.
- Build the schema and the gating checks now; the payment gateway integration and billing UI can
  land later without touching business modules.

## 12. VISUAL DESIGN SYSTEM — "Manifest"

No design was supplied, so this is the direction. **Follow it exactly; do not substitute a default
dashboard theme.** The users are operations staff in Dhaka doing data entry for eight hours a day.
The product's job is fast, error-free entry and retrieval of shipping records. Density, legibility
and scannability beat decoration everywhere.

The visual language is borrowed from the subject's own world: shipping manifests, stencilled
container markings, port schedules.

### Tokens (define once in `globals.css` and `tailwind.config.ts` — never hardcode a hex)

```
--hull        #10243A   sidebar, top bar, primary headings, body text
--steel       #6B7A88   secondary text, icons, placeholder
--harbour     #0F7173   primary action, links, focus ring, active nav
--harbour-ink #0A5254   hover on primary
--paper       #F4F6F5   app background
--surface     #FFFFFF   cards, tables, modals
--line        #DDE3E3   borders, dividers, table rules
--verified    #2F7A54   active / paid / approved
--signal      #C87A16   pending / awaiting / warning
--alert       #B3403A   inactive / overdue / destructive
```

Semantic tokens only in components: `bg-surface`, `text-steel`, `border-line`. Dark mode is out of
scope for v1 — do not build it half-way.

### Typography

- **UI + body: IBM Plex Sans.** Industrial, engineered register; also has a Bengali sibling
  (IBM Plex Sans Bengali) if the client localises later, so the family survives that decision.
- **All identifiers and all numbers: IBM Plex Mono** — business codes (`PL-001`), container and BL
  numbers, HS codes, rates, volumes, dates. **Use `font-variant-numeric: tabular-nums`.**
  This is the one signature move: digits align vertically down a column, so an operator scanning
  fifty container numbers sees a transposed digit instead of reading past it. Mono is a
  correctness tool here, not a style.
- Scale: page title 20px/600 · section 15px/600 · body + inputs 14px/400 · table cell 13px/400 ·
  label + column header 11px/600 uppercase, `0.06em` tracking, `--steel`.
- Numbers right-aligned. Text left-aligned. Column headers match their column's alignment.

### Layout shell

```
┌────────────┬───────────────────────────────────────────────┐
│            │ breadcrumb        [ search ]  [tenant] [user] │  56px top bar, surface, 1px --line
│  SIDEBAR   ├───────────────────────────────────────────────┤
│  240px     │  Page title                    [ + Add … ]    │
│  --hull    │  ┌─────────────────────────────────────────┐  │
│            │  │ search · filters                        │  │

└────────────┴───────────────────────────────────────────────┘
```

Sidebar: `--hull`, module groups collapsible, active item marked by a 3px `--harbour` left bar plus
a lighter fill. Only modules the user can see are rendered (§7 + §7B). No page-level max-width —
these tables need every pixel.

### Components

- **Table.** 36px rows (Compact 30px — ship a density toggle, persisted per user). Header row
  `--paper` with a bottom `--line`. Row hover `#F0F4F4`. Zebra striping off. **First data column is
  the business code in mono on a faintly tinted gutter** — the stencilled container-marking
  reference, and the anchor the eye returns to. Sticky header, sticky first column and sticky
  Action column on horizontal scroll.
- **Status.** Not a coloured pill. A 6px dot plus a label — `--verified` Active, `--steel`
  Inactive, `--signal` Pending, `--alert` Overdue. Quieter, and it survives a dense grid.
- **Actions.** Text buttons in `--harbour`, not icon-only — the users are not power users on day
  one. Destructive/deactivate in `--alert`. Hide what the user lacks permission for.
- **Forms.** Single column up to 8 fields, two columns beyond. Labels above inputs. 36px inputs,
  4px radius, 1px `--line`, focus = 2px `--harbour` ring. Required marked on the label, never by
  placeholder. Errors sit below the field in `--alert`, and name the fix.
- **Empty states** invite the action: "No carriers yet. Add your first carrier to start building
  price lists." Never a shrug and a blank box.
- **Radius 4px everywhere. One shadow only** (`0 1px 2px rgb(16 36 58 / 0.06)`) on cards, modals and
  dropdowns. No gradients, no glassmorphism, no illustration.
- **Motion:** 120ms ease-out on hover/focus, 160ms on modal entry. Nothing else. Respect
  `prefers-reduced-motion`.

### Quality floor (not optional)

Visible keyboard focus on every control · full keyboard navigation of tables and forms ·
WCAG AA contrast · works down to a 1280px laptop, and list screens remain usable on tablet ·
every destructive action confirms · every async action shows a pending state.
